## 系统架构

```
                              ┌──────────────────────────────────────────────┐
   OpenAI SDK / Codex CLI ──► │  8787  OAIprism 网关（oaiprism serve）        │
   Anthropic SDK          ──► │  ├─ /v1/*          OpenAI / Anthropic 门面    │
   curl / 任意 HTTP 客户端 ──► │  ├─ /prism/*       原样反代（白名单）          │
                              │  ├─ /admin/*       管理 API                   │
                              │  ├─ /dashboard/    Dashboard（web/dist）       │
                              │  └─ /healthz /readyz /metrics                  │
                              └───────────────┬──────────────────────────────┘
                                              │ 调优 HTTP 客户端（HTTP/2、连接预热）
                                              ▼
                              ┌──────────────────────────────────────────────┐
                              │  8790  Go TLS 桥（oaiprism tlsbridge）        │
                              │  Chrome 系 TLS 指纹传输；每请求向 8791 取      │
                              │  一次性 Sentinel token                         │
                              └───────────────┬──────────────────────────────┘
                                              │ 带 openai-sentinel-token
                                              ▼
                              ┌──────────────────────────────────────────────┐
                              │  8791  Sentinel token oracle（node + Chrome） │
                              │  在真实页面里执行 SentinelSDK.token()，只签发  │
                              └───────────────┬──────────────────────────────┘
                                              ▼
                                   prism.openai.com（Cloudflare 之后）
```

**一次推理**：客户端 → 8787（协议翻译为上游 start + 轮询）→ 8790（补 Sentinel token、
按浏览器指纹发出）→ 上游 → 8787 把轮询结果转成增量 SSE 推回客户端。

**为什么需要桥**：Cloudflare 拦截不具备浏览器信任特征的请求，写操作还需要
Sentinel 反自动化令牌。8790 解决"传输指纹"，8791 只负责"签发令牌"，
两者拆开后各自崩溃面小、可独立重启。

## 多轮上下文

### 结论（均为真实请求对照实验所得）

1. **上游单次请求只处理「最后一条 system + 最后一条 user」**，拼成
   `Context:
<system>

User request:
<user>` 一段文本，其余 input 条目全部丢弃
   （抓包 149 次 start 的 `turn_state.prompt` 无一例外；2026-10-04 双 system 暗号实测）；
2. **上游不会凭 `previousResponseId` 替我们拼接历史**（2026-10-03 实测：只发本轮增量 +
   上一轮句柄，第二轮必然失忆）；
3. 把历史折叠成 `[Previous Conversation History]` 文本并入 system，多轮记忆稳定可靠。

### 网关的做法

**每一轮都发送完整上下文**，且发往上游的 input 恰好是 `[system, user]`：全部 system /
developer / instructions 合并成唯一一条，历史挂在它末尾（`internal/facade/upstream_input.go`）。
多条 system 分开发时只有最后一条生效，挂在前面的历史随之丢失；中间条目发了也白发，
还会让输入用量虚高。

- 客户端自带历史（Codex CLI、标准 Chat / Anthropic 客户端）：历史折叠进 system；
- 客户端只发本轮消息：用网关的**会话链**（`internal/facade/session_chain.go`，
  最多 20 条 / 24k 字符，超限从最旧处裁剪）注入历史。Codex 桥请求每轮自带完整上下文，
  从不注入会话链。

会话链的身份来自**强会话标识**：`X-Oaiprism-Session`、Codex 的 `client_metadata` /
`prompt_cache_key`、请求体里的 `conversation_id` 等；Responses API 客户端也可以用标准的
`previous_response_id` 续接。首条消息指纹、`user` 字段这类**弱标识**只用于账号/项目亲和，
绝不据此注入历史 —— 两段以同一句话开头的对话会撞到同一个弱标识。

项目（工作区）在同一会话内复用；`facade.upstream_continuation`（默认关闭）决定是否额外把
上游会话句柄与沙箱快照（`conversationId` / `previousResponseId` / `codex_listen_snapshot`）
一并发给上游。若携带的句柄已失效，网关会丢弃句柄、用完整上下文原地重试一次。

### 上游的窗口与原生续接

- conversation 窗口约 **2M tokens**（浏览器内同一 conversation 连续 88 轮，1.92M tokens
  仍记得暗号）；单条消息上限约 **100 KiB（UTF-8 字节，不是 tokens）**，超限报错
  `This request is too large to send...`（见下一节）；
- 真实浏览器内的原生续接（同一 `conversationId` + 上一轮 `resp_*` + `codex_listen_snapshot`
  + 仅本轮增量）可以成功，但同样的请求经 Go 通道发出会失忆 —— 上游把非浏览器级信任的请求
  当作无状态会话。`tools/browser_forward.js`（浏览器全请求代发）是这一方向的实验件。

数据与脚本：`tools/webui_probe*.js`、`tools/webui_probe7_log.jsonl`、`tools/probe_context_limit.py`。

## 上下文压缩与单条上限

### 上游按字节限长

发往上游的 `[system, user]` 合计约 **100 KiB** 封顶（2026-10-04 实测）：

| 内容 | system + user 字节 | tokens | 结果 |
|---|---|---|---|
| 英文 | 102,299 | 21.9k | ✅ |
| 英文 | 104,560 | 22.2k | ❌ too large |
| 中文 | 约 98k | 32.3k | ✅ |
| 中文 | 约 104k | 34.5k | ❌ too large |

所以任何按 token 定的窗口都对不准：英文与代码约合 2 万多 tokens，中文约 3 万 tokens，
缩进多的内容（一个 token 占好几个字节）更少。网关按字节预检，上限是
`facade.max_prompt_bytes`（默认 96 KiB，给上游的包装文本留余量）。

超限请求若照发，代价很高：上游先回 too large，同一请求重发常变成
`Error while processing conversation (403)`，曾被当成沙箱未就绪重试 10 次（一次约 5 分钟）；
错误码又是 `server_error`，Codex 把它当断线重连 5 次，既不压缩也不裁历史 —— 会话就此卡死。
现在的处理：

- **历史裁到放得下**：折叠历史时按剩余字节预算裁掉最旧的部分（见下文），Codex 桥请求也一样；
- **本轮本身超限才失败**：system 加本轮消息就已经超限、裁历史也救不了时，在占用账号、
  建项目、申请沙箱之前就失败，不发上游。错误码按协议给：
  - Responses：`response.failed` + `context_length_exceeded`；
  - Chat：HTTP 400 + `context_length_exceeded`；
  - Anthropic：HTTP 400 + `prompt is too long: N tokens > M maximum`（Claude Code 认这句）。

  上游自己报 too large 时同样转成这个码。

为什么 Codex 的历史也由网关裁，而不是回 `context_length_exceeded` 等它压缩：实测 Codex 0.160
收到这个码只会结束本轮（`Codex ran out of room in the model's context window`），下一轮照发
同样的历史，并不会因此压缩；把窗口配成 272k 也一样。它只按网关回报的用量决定何时压缩。

### 历史折叠的预算

往轮对话折进 system 时按剩余字节预算处理（`internal/facade/compress.go`）：放得下就原样全留；
放不下时，先丢大块的工具输出与助手回复（从最旧的丢起），仍超再从最旧的起丢其余消息。用户自己说的话（交代的要求、给的暗号）最后才动，Codex 自己压缩时保留的也正是用户消息。丢掉的位置原地注明省略了几条、多少字节。

早期实现超过 6 轮就把早期消息截成前 197 个字，一段只有 481 tokens 的对话因此答不出
首轮给的暗号（同日实测，5 轮能答对、7 轮答"不知道"）。

### Codex 的压缩

本地 provider 不叫 OpenAI 时，Codex 在本地压缩：照常发一次 `/responses`，历史末尾附一条
`You are performing a CONTEXT CHECKPOINT COMPACTION…`，元数据里标
`request_kind=compaction`（`strategy=memento`），拿回复正文当摘要；之后用
"保留的用户消息 + 一条摘要"替换历史。网关的配合：

- **替换历史照样折叠**：它只有 user 消息与摘要、没有 assistant。早期"见过 assistant 才折叠"
  的判据会漏折，摘要被上游丢掉，再回落注入陈旧的会话链。实测把压缩后的首个请求换个空会话链
  重放，模型答"上下文未提供本任务的暗号"。现在桥请求一律折叠，从不注入会话链；
- **压缩请求必须成功**：它是整段会话里最大的一次请求，超过单条上限时同样裁掉最旧的历史。
  system 末尾注明只回摘要正文，回复一律按文本返回，不会变成工具调用。

想让 Codex 按时压缩（而不是靠网关裁），就在 Codex 里把 `model_context_window` 设成与上游
上限相当的值（见使用指南）。Codex 不会向自定义 provider 查询 `/v1/models`，网关没法替它设。

本地 Codex 发来的 developer 消息里，基础提示词（`You are Codex…`，约 21.7 KB）与多代理
说明不转发，见下一节。

## 上游提示词分层

上游模型跑在沙箱里的 Codex CLI（2026-10-04 实测 `codex-cli 0.156.0`，工作目录
`/codex_workspace/<项目 UUID>`）。它看到的提示词从上到下是：

| 层 | 来源 | 网关的处理 |
|---|---|---|
| Codex 基础指令 | 沙箱 Codex 本体 + Prism 的模型目录（`/opt/codex/model-catalog.json`） | 请求侧无法去除 |
| developer 消息 | Codex 自动生成（权限、沙箱策略等） | 请求侧无法去除 |
| AGENTS.md | Prism 每轮写进工作区的 7 条 LaTeX 编辑器规则（约 240 tokens） | 点名作废 |
| `<environment_context>` | Codex 自动生成（shell=bash、cwd=/codex_workspace/…） | 点名作废 |
| 本轮消息 | 网关发的 `Context: … User request: …` | 完全由网关决定 |

结论来自真实请求：上游没有可用的指令字段（`metadata` 里的 `instructions`、
`developer_instructions`、`base_instructions` 等六个候选字段实测全部无效），
我们发的 system 到了上游也只是 user 层文本。后两层与我们同级，网关的做法是"后到 + 点名作废"：

- **Codex 桥请求**：本地 Codex CLI 发来的 AGENTS.md（全局与项目，上限 12k 字符）与
  `<environment_context>` 搬进 system 的 `<client_project_instructions>` /
  `<client_environment>` 段，声明它们是唯一有效的规则；桥指令末尾的
  `PLATFORM INSTRUCTIONS VOID` 引用 Prism AGENTS.md 的首句，宣布其不适用。
  本地 Codex 的基础提示词不转发。Codex 0.160 起它不在顶层 `instructions`，而是首条
  developer 消息（`You are Codex…`，约 21.7 KB）。沙箱 Codex 已有同类指令，再带一份只会
  挤占单条上限：实测桥 system 光固定部分就有 37.5 KB，6 轮短对话就触发了压缩。
  `<multi_agent_role>` / `<multi_agent_mode>`（派生子代理）同样不转发，因为桥只提供
  `exec_command`。权限、skills 与用户自定义的 developer 指令照常转发。
- **其他请求**：system 最前面加一段 `<gateway_notice>`，同样点名作废（`facade.platform_notice`，默认开启）。
  兜底系统提示是不带平台人设的中性提示。

沙箱里的 `~/.codex/config.toml` 对沙箱用户可写，改它能真正去掉 AGENTS.md 甚至替换基础指令，
但那是在改平台自己的 Agent 配置，风险最高、持久性未知，网关不这样做。

## Codex 工具桥

上游是 server-side tools 架构：模型的终端/文件工具在**上游容器**里执行，客户端只拿到最终
文本 —— 本地 Codex CLI 的工具一次都不会被调用，"创建"的文件也不在你的磁盘上。

工具桥反过来：在 system 指令里告诉模型"没有执行环境，所有操作必须输出一个
```` ```codex-exec ```` 代码块"；网关把代码块翻译成 Responses 协议的工具调用
（`custom_tool_call` 或 `function_call`，按 CLI 实际注册的工具类型与名字），Codex CLI
在本地执行并回传结果，网关再把结果翻译回上下文。工具声明的两条路径（input 内
`additional_tools`、顶层 `tools`）都能识别。

若模型没有输出代码块、却在上游容器里改了文件（DeltaFiles），网关会把变更合成为本地命令：

- **新增文件**按完整内容写入（Base64 传递，无转义问题；Windows 大文件分块，规避
  32,767 字符的命令行上限）；
- **修改**一律按"在本地文件中定位原文 → 替换"落地，保留原换行风格与 BOM；
  定位不到就报错、**不改文件**；
- 路径必须是工作区内的相对路径，并按 PowerShell / POSIX shell 规则转义。

## 上游协议（已实测校准）

> 详见 [协议校准报告](协议校准报告.md) 与 [Prism 完整调用链](Prism完整调用链.md)。

推理端点：`/api/llm/response_with_tools_{start,status,stop}`。

```jsonc
// POST /api/llm/response_with_tools_start
{"input":[{"type":"message","role":"user","content":[{"type":"input_text","text":"…"}]}],
 "metadata":{"model":"gpt-6.1-sol",          // 模型参数在 metadata 里，不在顶层
             "reasoning_effort":"medium",
             "projectId":"…",
             "frontend_origin":"https://prism.openai.com"}}
// → {"status":"started","request_id":"…","turn_state":{…}}        需要轮询
// → {"status":"completed","request_id":"…","response":{…}}        已经结束

// POST /api/llm/response_with_tools_status   必须带 {request_id, turn_state}
// → {"status":"pending","turn_state":{…新令牌…}}
// → {"status":"completed","response":{"status":"success","payload":{"output":[…]}}}
// 答案在 response.payload.output[-1].content[*].text（只取最后一条，多轮下会累积）
```

三个反直觉的点：

1. **失败是 HTTP 200**：`status:"completed"` + `response.status:"error"`，只看状态码会得到空回答；
2. **`turn_state` 是续令牌**，每轮换新且必须原样回传，自造值会被拒；
3. **大小写不统一**：start 用 `conversationId`，status 用 `request_id`，不要"顺手统一"。

`start` 不是幂等操作：网关只对确定未送达的失败（建连失败、429/503）重试，避免在同一会话上
重复发起生成。字段名都可通过 `facade.schema` 配置，上游变化时不必重新编译。

## 沙箱

> 详见 [Yjs 依赖调研与沙箱方案](Yjs依赖调研与沙箱方案.md)。

上游的 AI 在容器沙箱里工作，并且需要项目工作区。网关自动完成全部前置步骤：

```
1. POST /api/backend/1/new                          申请沙箱 → {url, token}
2. POST /api/projects/{id}/sandbox/resources-token  签发资源令牌（绑定项目，1 小时）
3. POST <sandbox>/resources-token                   交给沙箱
4. POST /api/y                                      取 Y-Sweet 文档凭证
5. POST <sandbox>/token                             原样交给沙箱
6. GET  <sandbox>/wait-for-sync                     等待 status=synced
```

第 5 步之后是沙箱自己同步文档，网关不需要实现 Yjs。漏掉任何一步，沙箱都不报错，只会一直停在
`syncing`，表现为会话**固定 122 秒**后 504（`Please submit prompt again.`）。

- 认证是双重的：`X-Crixet-Sandbox-Token` + Cookie，只带前者会得到空响应体的 401；
- 沙箱按账号缓存，工作区同步状态按（账号, 项目）缓存，过期点与资源令牌一致；
- 冷启动未就绪时原地退避重试，只有明确断连或连续 5 次未就绪才重建容器；
- 实测延迟：首次（建项目 + 申请沙箱 + 同步 + 生成）约 14 s，同会话后续请求约 5–6 s。

## 安全设计

- **鉴权默认收紧**：没有任何 Key 时只放行本机；管理端与 API 权限分离（见[使用指南](使用指南.md#鉴权与-api-key)）。
- **不读取调用方指定的本地文件**：`image_url` 只接受 `data:image/*` 与解析到公网地址的
  http(s) 链接，建连时二次校验地址（防 DNS rebinding），且内容必须真的是图片。
- **上游产物落地受控**：只写工作区内相对路径；修改不做整体覆盖；`X-Local-Workspace` 默认关闭。
- **原样反代**：丢弃调用方的 `Authorization` / `Cookie`，绝不回传上游 `Set-Cookie`，
  白名单按路径段匹配。
- **会话隔离**：会话链按调用方 Key 指纹隔离，弱会话标识不继承上下文。
- **凭据**：`/admin/accounts` 不返回凭据内容；凭据文件 `0600` 写入；请求流水记录的账号与
  客户端 IP 不信任客户端可伪造的请求头。
- **OAuth 回调**：`state` 必须精确匹配。

## 性能设计

- **连接**：`MaxIdleConnsPerHost: 256`、启动预热 TCP/TLS、出站强制 HTTP/2、关闭自动 gzip；
- **流式**：SSE 缓冲来自 `sync.Pool`，手写 JSON 转义，每个增量立即 `Flush`，
  并设置 `X-Accel-Buffering: no`（否则 Nginx 会把整段流缓冲到结束）；
- **轮询转流式**：无条件节流（不会退化成忙轮询）、空轮询自适应退避、前缀差分还原 token 级增量；
  等待上游期间持续发送心跳，避免中间链路按空闲断开；
- **项目复用**：建项目比推理本身还慢，同一会话只建一次；无会话标识的请求轮转分桶；
- **账号粘性**：命中即续期；粘性账号仅因并发已满时短暂等待，而不是立刻换号；
- **指标**：`oaiprism_facade_first_delta_seconds` 直接衡量首字延迟。

## 用量计数

上游从不返回 usage（轮询响应的顶层与 payload 都没有这个字段），网关按本轮实际收发的内容自行计数：

- **分词**：官方 o200k_base 词表（与 tiktoken 校验的 sha256 一致，内嵌进二进制，运行时不联网）
  + 官方预切分正则 + 标准 BPE 合并，结果与 `tiktoken.encode_ordinary` 逐 token 一致。
  对拍样本：仓库全部源码与文档（41 万 token）、空白与换行的全部短组合、4500 条随机 Unicode，零差异；
- **输入**：真正发往上游的 input 条目（规整为 `[system, user]` 之后，即上游实际会读的内容），按 OpenAI 官方口径计入消息帧开销（每条 3 + 角色名，
  末尾回复引导 3）；图片按视觉计费规则（low 85；high/auto 缩放后按 512 切块，每块 170 + 85），
  data URI 解析真实宽高；
- **输出**：生成正文 + 推理文本，推理部分另记 `reasoning_tokens`（已含在输出内）；
- **去向**：同一组数字返回给客户端（Chat / Responses / Anthropic 三种 usage 结构），
  并写入请求流水，统计页按模型、按小时汇总；
- **防护**：BPE 原算法对单个超长片段是 O(n²)（2MB 连续字母会让计数永远算不完），
  长片段改用堆合并，O(n log n) 且合并顺序不变；Codex 每轮重发的历史块按内容缓存计数。

无法观测的部分不计：上游沙箱内部追加的系统提示与隐藏推理 token 不在收发内容里。
