## 系统架构

```
                              ┌──────────────────────────────────────────────┐
   OpenAI SDK / Codex CLI ──► │  8787  OAIprism 网关（oaiprism serve）        │
   Anthropic SDK          ──► │  ├─ /v1/*          OpenAI / Anthropic 门面    │
   curl / 任意 HTTP 客户端 ──► │  ├─ /prism/*       原样反代（白名单）          │
                              │  ├─ /admin/*       管理 API                   │
                              │  ├─ /dashboard/    Dashboard（web/dist）       │
                              │  └─ /healthz /readyz /metrics                  │
                              │                                                │
                              │  出站：Chrome 指纹传输（internal/upstream）     │
                              │  ├─ Chrome 的 TLS / HTTP2 指纹与请求头          │
                              │  ├─ Prism 会话换发（/auth/session）            │
                              │  └─ Sentinel 签发（internal/sentinel）：       │
                              │     goja 里原样执行官方 sdk.js                 │
                              └──────────┬───────────────────────┬───────────┘
                                         │ 带 OpenAI-Sentinel-Token│ sentinel/req
                                         ▼                         ▼
                              prism.openai.com           sentinel.openai.com
                              （Cloudflare 之后）
```

**一次推理**：客户端 → 8787（协议翻译为上游 start + 轮询；需要的请求现签 Sentinel token，
以 Chrome 指纹直连）→ 上游 → 8787 把轮询结果转成增量 SSE 推回客户端。

**只有一个进程**：Cloudflare 拦截不具备浏览器传输特征的请求，写操作还需要 Sentinel 反自动化令牌。
这两件事以前分别由 8790 TLS 桥和 8791 浏览器 oracle（Node + 真实 Chrome）承担；现在都在网关进程里
用纯 Go 完成，见 [Sentinel 纯 Go 签发](#sentinel-纯-go-签发)。

## 多轮上下文

### 结论（均为真实请求对照实验所得）

1. **上游单次请求只处理「最后一条 system + 最后一条 user」**，拼成
   `Context:
<system>

User request:
<user>` 一段文本，其余 input 条目全部丢弃
   （抓包 149 次 start 的 `turn_state.prompt` 无一例外；2026-10-04 双 system 暗号实测）；
2. **上游按会话 ID 保存完整对话**，但只认经前端 Server Action 登记过的会话：带登记过的
   `conversationId`、每轮只发增量，第二轮起照样记得前文；不带会话 ID 时上游临时分配一个，
   这种会话不续接（把临时 ID 带回去也不续接）；自造的 ID 直接 403。2026-10-03 "只发增量
   必然失忆"的结论就是没登记会话造成的（2026-10-04 Go 侧对照实验）；
3. 上游一条消息约 **100 KiB**（UTF-8 字节）封顶，所以不能每轮把整段历史塞进一条消息。

### 原生续接

会话历史交给上游保管（`internal/facade/native.go`）：

- **登记会话**：客户端会话第一次出现时，网关调用前端的 Server Action
  `createProjectConversation(projectId)` 在项目下登记一个会话（`cdx1_<uuid>`），之后每轮都带它。
  Action ID 随前端构建变化，失效（404）时网关从首页引用的脚本里重新找（`internal/prism/server_action.go`）；
- **只发增量**：客户端（Codex、Chat 客户端）每轮仍发完整历史。网关按条目指纹比对已送达的前缀，
  只把之后的新条目拼成 `[system, user]` 发出（实测 Codex 读文件结果那一轮 848 字节，追问 586 字节）。
  只发本轮消息的客户端（Responses 的 `previous_response_id`、带回 `conversation_id` /
  `x-prism-conversation-id` 的客户端）凭句柄找回会话，直接追加；
- **system 不每轮重发**：桥指令约 13 KB，上游会话里已有。内容变了、或距上次完整发送累计超过 48 KiB
  时重发一次（长会话里离得太远的指令约束力会变弱），其余轮次用一句话代替；
- **防串话**：强会话标识（Codex 会话 ID、`X-Oaiprism-Session` 等）下按用户 / 工具条目比对；
  弱标识（首条消息指纹）会撞，连助手原文一起比对 —— 同一句话开头的两段对话不会进同一个上游会话；
- **Codex 压缩**：压缩请求在上游会话里直接让上游写摘要（它握有完整记忆）；压缩后的替换历史里认出
  这段摘要，继续用同一个会话；
- **绑定落盘**：客户端会话 → 上游会话的绑定存进 SQLite（`native_bindings` 表，7 天未用清理），
  网关重启后照样接回原来的上游会话；
- **对不上就重建**：换了账号、客户端改写了历史、会话作废（`conversation_too_large`、not found）时
  新建会话。历史一条放得下就随首轮发出；放不下就先**分段补种**（每段一轮，只补最近的约 768 KiB），
  再发本轮 —— 实测网关从没见过的 200 KB 历史分 3 段补种，答出了最早一条里的暗号；
  登记会话本身失败时，这一轮退回不带会话 ID 的单条全量（按单条上限裁剪），下一轮再登记；
- **用量**按客户端视角的完整上下文计，Codex 据此判断何时压缩本地历史。

#### 上限实测

2026-10-04，同一个上游会话连续灌入 51 段随机字母（每段约 4.5 万 tokens，约 2 字节/token，
本身就接近单条上限），每 3 段插一次提问，问最早还没问过的那一段的校验码与开头 6 个字母
（摘要不可能保留随机字母，答得出说明原文还能看到）：

| 累计 | 结果 |
|---|---|
| 13.5 万 ~ 149 万 tokens | 11 次提问全部逐字答对（段 1 ~ 段 11） |
| 162 万 ~ 230 万 tokens | 续跑同一会话，回头再问段 1 ~ 段 6，同样逐字答对 |

会话本身始终没有报错（没有 `conversation_too_large`），没有测到上限。灌到约 230 万 tokens 时账号被
上游限流（新开的会话同样 403、`Request verification failed`），测试就此中止 —— 一小时里灌了两百多万
tokens，这是账号层面的频率限制，不是会话上限。

每轮耗时稳定在 10 ~ 20 秒，不随会话变长而增加：上游不是每轮把全文喂给模型，而是自己管理长会话；
但对早期内容的逐字提问每次都答对了。沙箱闲置 25 分钟被回收、换了新沙箱后，同一会话仍记得暗号。

### 单条全量的用途

发往上游的 input 恰好是 `[system, user]`：全部 system / developer / instructions 合并成唯一一条
（`internal/facade/upstream_input.go`）。多条 system 分开发时只有最后一条生效，中间条目发了也白发。

客户端自带的历史折叠进这条 system（超过单条上限时从最旧处裁剪，见下一节）。这份"单条全量"只在
两种时候发出：新建上游会话的首轮（历史放得下时），以及登记会话失败、补种失败时的回退。

会话的身份来自**强会话标识**：`X-Oaiprism-Session`、Codex 的 `client_metadata` /
`prompt_cache_key`、`conversation_id` 等；Responses API 客户端也可以用标准的
`previous_response_id` 续接。首条消息指纹、`user` 字段这类**弱标识**会撞，只用于账号/项目亲和，
续接时必须连助手原文一起比对。

数据与脚本：`tools/webui_probe*.js`、`tools/webui_probe7_log.jsonl`、`tools/probe_context_limit.py`。

## 上下文压缩与单条上限

### 上游按字节限长

发往上游的 `[system, user]` 合计约 **100 KiB** 封顶（2026-10-04 实测）：

| 内容 | system + user 字节 | tokens | 结果 |
|---|---|---|---|
| 英文 | 102,299 | 21.9k | ✅ |
| 英文 | 104,560 | 22.2k | ❌ too large |
| 中文 | 约 98k | 32.3k | ✅ |
| 中文 | 约 104k | 34.5k | ❌ too large |

所以任何按 token 定的窗口都对不准：英文与代码约合 2 万多 tokens，中文约 3 万 tokens，
缩进多的内容（一个 token 占好几个字节）更少。网关按字节预检，上限是
`facade.max_prompt_bytes`（默认 96 KiB，给上游的包装文本留余量）。

超限请求若照发，代价很高：上游先回 too large，同一请求重发常变成
`Error while processing conversation (403)`，曾被当成沙箱未就绪重试 10 次（一次约 5 分钟）；
错误码又是 `server_error`，Codex 把它当断线重连 5 次，既不压缩也不裁历史 —— 会话就此卡死。
现在的处理：

- **历史裁到放得下**：折叠历史时按剩余字节预算裁掉最旧的部分（见下文），Codex 桥请求也一样；
- **本轮本身超限才失败**：system 加本轮消息就已经超限、裁历史也救不了时，在占用账号、
  建项目、申请沙箱之前就失败，不发上游。错误码按协议给：
  - Responses：`response.failed` + `context_length_exceeded`；
  - Chat：HTTP 400 + `context_length_exceeded`；
  - Anthropic：HTTP 400 + `prompt is too long: N tokens > M maximum`（Claude Code 认这句）。

  上游自己报 too large 时同样转成这个码。

为什么 Codex 的历史也由网关裁，而不是回 `context_length_exceeded` 等它压缩：实测 Codex 0.160
收到这个码只会结束本轮（`Codex ran out of room in the model's context window`），下一轮照发
同样的历史，并不会因此压缩；把窗口配成 272k 也一样。它只按网关回报的用量决定何时压缩。

### 历史折叠的预算

往轮对话折进 system 时按剩余字节预算处理（`internal/facade/compress.go`）：放得下就原样全留；
放不下时，先丢大块的工具输出与助手回复（从最旧的丢起），仍超再从最旧的起丢其余消息。用户自己说的话（交代的要求、给的暗号）最后才动，Codex 自己压缩时保留的也正是用户消息。丢掉的位置原地注明省略了几条、多少字节。

早期实现超过 6 轮就把早期消息截成前 197 个字，一段只有 481 tokens 的对话因此答不出
首轮给的暗号（同日实测，5 轮能答对、7 轮答"不知道"）。

### Codex 的压缩

本地 provider 不叫 OpenAI 时，Codex 在本地压缩：照常发一次 `/responses`，历史末尾附一条
`You are performing a CONTEXT CHECKPOINT COMPACTION…`，元数据里标
`request_kind=compaction`（`strategy=memento`），拿回复正文当摘要；之后用
"保留的用户消息 + 一条摘要"替换历史。网关的配合：

- **替换历史接回同一个会话**：它只有 user 消息与摘要、没有 assistant。网关认出摘要（上游刚在
  这个会话里写的），从它之后只发新消息；必须新建会话时，替换历史整段折叠或补种过去；
- **压缩请求必须成功**：它是整段会话里最大的一次请求，超过单条上限时同样裁掉最旧的历史。
  system 末尾注明只回摘要正文，回复一律按文本返回，不会变成工具调用。

Codex 不会向自定义 provider 查询 `/v1/models`，`model_context_window` 网关没法替它设（推荐值见
使用指南）。单条上限只约束增量，这一节的裁剪只发生在新建会话的首轮与回退时。

本地 Codex 发来的 developer 消息里，基础提示词（`You are Codex…`，约 21.7 KB）与多代理
说明不转发，见下一节。

## 上游提示词分层

上游模型跑在沙箱里的 Codex CLI（2026-10-04 实测 `codex-cli 0.156.0`，工作目录
`/codex_workspace/<项目 UUID>`）。它看到的提示词从上到下是：

| 层 | 来源 | 网关的处理 |
|---|---|---|
| Codex 基础指令 | 沙箱 Codex 本体 + Prism 的模型目录（`/opt/codex/model-catalog.json`） | 请求侧无法去除 |
| developer 消息 | Codex 自动生成（权限、沙箱策略等） | 请求侧无法去除 |
| AGENTS.md | Prism 每轮写进工作区的 7 条 LaTeX 编辑器规则（约 240 tokens） | 点名作废 |
| `<environment_context>` | Codex 自动生成（shell=bash、cwd=/codex_workspace/…） | 点名作废 |
| 本轮消息 | 网关发的 `Context: … User request: …` | 完全由网关决定 |

结论来自真实请求：上游没有可用的指令字段（`metadata` 里的 `instructions`、
`developer_instructions`、`base_instructions` 等六个候选字段实测全部无效），
我们发的 system 到了上游也只是 user 层文本。后两层与我们同级，网关的做法是"后到 + 点名作废"：

- **Codex 桥请求**：本地 Codex CLI 发来的 AGENTS.md（全局与项目，上限 12k 字符）与
  `<environment_context>` 搬进 system 的 `<client_project_instructions>` /
  `<client_environment>` 段，声明它们是唯一有效的规则；桥指令末尾的
  `PLATFORM INSTRUCTIONS VOID` 引用 Prism AGENTS.md 的首句，宣布其不适用。
  本地 Codex 的基础提示词不转发。Codex 0.160 起它不在顶层 `instructions`，而是首条
  developer 消息（`You are Codex…`，约 21.7 KB）。沙箱 Codex 已有同类指令，再带一份只会
  挤占单条上限：实测桥 system 光固定部分就有 37.5 KB，6 轮短对话就触发了压缩。
  `<multi_agent_role>` / `<multi_agent_mode>`（派生子代理）同样不转发，因为桥只提供
  `exec_command`。权限、skills 与用户自定义的 developer 指令照常转发。
- **其他请求**：system 最前面加一段 `<gateway_notice>`，同样点名作废（`facade.platform_notice`，默认开启）。
  兜底系统提示是不带平台人设的中性提示。

沙箱里的 `~/.codex/config.toml` 对沙箱用户可写，改它能真正去掉 AGENTS.md 甚至替换基础指令，
但那是在改平台自己的 Agent 配置，风险最高、持久性未知，网关不这样做。

## Codex 工具桥

上游是 server-side tools 架构：模型的终端/文件工具在**上游容器**里执行，客户端只拿到最终
文本 —— 本地 Codex CLI 的工具一次都不会被调用，"创建"的文件也不在你的磁盘上。

工具桥反过来：在 system 指令里告诉模型"没有执行环境，所有操作必须输出一个
```` ```codex-exec ```` 代码块"；网关把代码块翻译成 Responses 协议的工具调用
（`custom_tool_call` 或 `function_call`，按 CLI 实际注册的工具类型与名字），Codex CLI
在本地执行并回传结果，网关再把结果翻译回上下文。工具声明的两条路径（input 内
`additional_tools`、顶层 `tools`）都能识别。

若模型没有输出代码块、却在上游容器里改了文件（DeltaFiles），网关会把变更合成为本地命令：

- **新增文件**按完整内容写入（Base64 传递，无转义问题；Windows 大文件分块，规避
  32,767 字符的命令行上限）；
- **修改**一律按"在本地文件中定位原文 → 替换"落地，保留原换行风格与 BOM；
  定位不到就报错、**不改文件**；
- 路径必须是工作区内的相对路径，并按 PowerShell / POSIX shell 规则转义。

写文件首选 Codex 自带的补丁工具：客户端在 exec 脚本里提供 `tools.apply_patch` 时（code mode），
桥指令让模型直接调用它，不经 shell，任何系统都一样。模型仍把 `apply_patch <<'PATCH' …` 当 shell
命令写出来时，网关在交给客户端前改写：有原生工具就改调 `tools.apply_patch`（补丁正文按 JSON 转义，
反引号与 `${` 都不怕）；没有、且客户端是 Windows，就把补丁翻译成 PowerShell 文件操作 —— PowerShell
没有 heredoc，原样执行只会报"重定向运算符后缺少文件规范"。

用户附的图片在上游的**项目沙箱**里，不在本地磁盘：桥指令允许模型用内置的只读工具
（`view_image`）打开它们，见[沙箱 · 附件](#附件图片)。

## 上游协议（已实测校准）

> 详见 [协议校准报告](协议校准报告.md) 与 [Prism 完整调用链](Prism完整调用链.md)。

推理端点：`/api/llm/response_with_tools_{start,status,stop}`。

```jsonc
// POST /api/llm/response_with_tools_start
{"input":[{"type":"message","role":"user","content":[{"type":"input_text","text":"…"}]}],
 "metadata":{"model":"gpt-6.1-sol",          // 模型参数在 metadata 里，不在顶层
             "reasoning_effort":"medium",
             "projectId":"…",
             "frontend_origin":"https://prism.openai.com"}}
// → {"status":"started","request_id":"…","turn_state":{…}}        需要轮询
// → {"status":"completed","request_id":"…","response":{…}}        已经结束

// POST /api/llm/response_with_tools_status   必须带 {request_id, turn_state}
// → {"status":"pending","turn_state":{…新令牌…}}
// → {"status":"completed","response":{"status":"success","payload":{"output":[…]}}}
// 答案在 response.payload.output[-1].content[*].text（只取最后一条，多轮下会累积）
```

三个反直觉的点：

1. **失败是 HTTP 200**：`status:"completed"` + `response.status:"error"`，只看状态码会得到空回答；
2. **`turn_state` 是续令牌**，每轮换新且必须原样回传，自造值会被拒；
3. **大小写不统一**：start 用 `conversationId`，status 用 `request_id`，不要"顺手统一"。

`start` 不是幂等操作：网关只对确定未送达的失败（建连失败、429/503）重试，避免在同一会话上
重复发起生成。字段名都可通过 `facade.schema` 配置，上游变化时不必重新编译。

## Sentinel 纯 Go 签发

Prism 的写请求都要带 `OpenAI-Sentinel-Token`。按前端 `withPrismSentinel` 的规则，范围是 `/api/` 下除登录、
埋点等少数端点外的全部请求（**连轮询 GET 也要**）、Server Action（带 `next-action` 头）与沙箱代理。
令牌由 `sentinel.openai.com` 下发的 sdk.js 在浏览器里生成：

```
token = {"p": 工作量证明, "t": dx 虚拟机的指纹采集结果, "c": 一次性挑战令牌, "flow": "prism_inference"}

1. 页面用 25 项浏览器参数算 requirements PoW（fnv 哈希），隐藏 iframe 把它 POST 给 sentinel/req
2. 响应带回 c、PoW 难度，以及加密的 dx 程序（XOR 密钥就是第 1 步的 PoW 结果）
3. SDK 自带的寄存器虚拟机执行 dx：采集屏幕、navigator、localStorage 键、字体测量、计时……，结果加密成 t
4. 按服务端难度再算一次 PoW 得到 p
```

**做法：不重写虚拟机，原样执行官方 SDK。** 网关在 goja（纯 Go 的 ECMAScript 引擎）里搭一个
"Chrome 打开 Prism 首页"的页面，执行线上的 sdk.js，调 `SentinelSDK.token()`。PoW、虚拟机、加密都是
SDK 自己的代码，OpenAI 换题型、改虚拟机都会自动跟上；网关只负责 SDK 看到的浏览器
（`internal/sentinel/browser.js`）：

- **形状**：接口挂在原型上、`Symbol.toStringTag`、原生函数的 `toString`、`Object.keys(window)` 的键序，
  取值来自 Profile（一台真实 Chrome 的快照，见[使用指南](使用指南.md#浏览器指纹)）；
- **V8 的细节**：报错文案（`Cannot read properties of undefined (reading 'x')` —— dx 会把 `""+err` 采进指纹）、
  `Math.random` 的 52 位精度（影响 `""+Math.random()` 的长度）、`performance.now()` 的 100 µs 粗化与浮点尾巴、
  `Date#toString` 的时区名；
- **字体测量**：Helvetica / Arial 都落到 Arial，按字形宽度累加、先做 NFC（`U` + U+031B 会合成更宽的 `Ư`）、
  行高随页面 CSS（1.5）、按 1/64 px 的 LayoutUnit 取整，与 Chrome 实测逐像素一致；
- **iframe 那一半**：frame.html 里的逻辑在 Go 里照搬（`frame.go`）—— sentinel/req 用 Chrome 指纹发出，
  540 秒缓存、出完令牌 5 秒后预取、4 秒取不到回错误载荷，都和 SDK 一致。

**验证**：用真实 Chrome 抓到的同一个挑战离线回放，除随机数与本机 localStorage 外，所有采集槽位与 Chrome
逐字节相同；对线上随机抽取的多种 dx 变体做环境审计，没有读到 Chrome 里不存在的属性。

**性能**：SDK 用 `r += String.fromCharCode(…)` 逐字 XOR 解约 2 万字符的 dx，V8 的 rope 让它是线性的，
在 goja 里却是平方级（一次几百 MB 临时字符串）。把这两个 XOR 函数换成语义相同的原生实现
（函数形状对不上就保持原样）后，本地计算 10–50 ms，另加一次 sentinel/req 往返；SDK 自己的预取
会把下一次的往返提前做掉。

**传输层**（`internal/upstream`）：

- Cloudflare 校验 JA3/JA4，标准库 TLS 过不去，出站用 `bogdanfinn/tls-client` 的 Chrome 指纹：
  模板按指纹的 Chrome 版本自动选（不新于它的最新模板；升级依赖后有新模板会自动用上）；
  扩展顺序每个连接随机打乱（Chrome 110 起如此，JA3 每次变、JA4 不变）；trust_anchors 扩展用
  `oaiprism profile -capture` 从本机 Chrome 采到的原样内容。实测与 Chrome 154 的 JA4、peetprint、
  HTTP/2 指纹完全一致；
- User-Agent、`sec-ch-ua`、`Accept-Language`、`Priority` 与请求头顺序都与 Profile 一致；
- Cookie 只带 access token 与 6 小时一换的 `prism_session_token`，不带 `Authorization`；
- 签发失败时与前端一样发 `{"e":"prism_sdk_unavailable"}` 占位，不会卡住请求；
- 整个进程只开一个"标签页"：签发串行（前端也是），页面每 6 小时重开一次，像用户刷新了网页；
- 非 `prism.openai.com` 的上游（测试、`tools/mock_upstream.py`）仍走标准库，不签令牌。

自检：`oaiprism sentinel -n 3` 只连 `sentinel.openai.com` 签几个令牌并解读内容，不需要账号。

## 沙箱

> 详见 [Yjs 依赖调研与沙箱方案](Yjs依赖调研与沙箱方案.md)。

上游的 AI 在容器沙箱里工作，并且需要项目工作区。网关自动完成全部前置步骤：

```
1. POST /api/backend/1/new                          申请沙箱 → {url, token}
2. POST /api/projects/{id}/sandbox/resources-token  签发资源令牌（绑定项目，1 小时）
3. POST <sandbox>/resources-token                   交给沙箱
4. POST /api/y                                      取 Y-Sweet 文档凭证
5. POST <sandbox>/token                             原样交给沙箱
6. GET  <sandbox>/wait-for-sync                     等待 status=synced
```

第 5 步之后是沙箱自己同步文档。漏掉任何一步，沙箱都不报错，只会一直停在
`syncing`，表现为会话**固定 122 秒**后 504（`Please submit prompt again.`）。

- 认证是双重的：`X-Crixet-Sandbox-Token` + Cookie，只带前者会得到空响应体的 401；
- 沙箱按账号缓存，工作区同步状态按（账号, 项目）缓存，过期点与资源令牌一致；
- 冷启动未就绪时原地退避重试，只有明确断连或连续 5 次未就绪才重建容器；
- 实测延迟：首次（建项目 + 申请沙箱 + 同步 + 生成）约 14 s，同会话后续请求约 5–6 s。

### 附件（图片）

上游**不会把 `input_image` 的像素交给模型**（会话里只剩一个 `[image]` 占位）。模型看图靠的是在沙箱里
用 `view_image` 打开项目文件；官方前端也是这么做的：把附件传进项目的 `prism-uploads/` 目录，
再用 `input_file`（`project_path: "/prism-uploads/<文件名>"`）引用。网关照做：

1. `POST /api/project-files/upload` 上传（`x-prism-file-id` 即文件节点 id）；
2. **登记进项目文件树**：文件树是 Y-Sweet 托管的 Yjs 文档（根 Map `content`：节点 id → `{id, filename,
   type, inFolder, deleted}`；`settings.init`）。只上传不登记，沙箱里就没有这个文件。网关经 Y-Sweet 的
   HTTP 接口读文档（`GET {baseUrl}/as-update`）、写入新增节点（`POST {baseUrl}/update`），编解码是
   `internal/ydoc` 里约 600 行的纯 Go 实现（只覆盖文件树用到的 Map 与基本值），不引入 CRDT 依赖；
3. 引用时附一句"在工作目录下的相对路径 `prism-uploads/<文件名>` 打开" —— 上游把它渲染成
   `[project file: /prism-uploads/…]`，模型照字面会去开文件系统根下的路径；工作目录其实是
   `/codex_workspace/<会话 id>`；
4. **沙箱只把它第一次同步的项目、当时已登记的文件落进工作区**：之后登记的文件、再同步的别的项目的文件
   都不会出现（重新交付令牌也不行）。所以项目里有比当前沙箱更新的附件、或沙箱落的是别的项目时，
   网关换一个新沙箱（多几秒，只在带新图片的那一轮）。

Codex 给本地图片加的 `<image name=[Image #1] path="F:\…">` 标签里的本机路径会被去掉，免得模型去沙箱里找它。

## 安全设计

- **鉴权默认收紧**：没有任何 Key 时只放行本机；管理端与 API 权限分离（见[使用指南](使用指南.md#鉴权与-api-key)）。
- **不读取调用方指定的本地文件**：`image_url` 只接受 `data:image/*` 与解析到公网地址的
  http(s) 链接，建连时二次校验地址（防 DNS rebinding），且内容必须真的是图片。
- **上游产物落地受控**：只写工作区内相对路径；修改不做整体覆盖；`X-Local-Workspace` 默认关闭。
- **原样反代**：丢弃调用方的 `Authorization` / `Cookie`，绝不回传上游 `Set-Cookie`，
  白名单按路径段匹配。
- **会话隔离**：会话链按调用方 Key 指纹隔离，弱会话标识不继承上下文。
- **凭据**：`/admin/accounts` 不返回凭据内容；凭据文件 `0600` 写入；请求流水记录的账号与
  客户端 IP 不信任客户端可伪造的请求头。
- **OAuth 回调**：`state` 必须精确匹配。

## 性能设计

- **连接**：Prism 出站经 Chrome 指纹传输复用 HTTP/2 连接，响应在传输层解压；
  其他上游用调优过的标准库客户端（`MaxIdleConnsPerHost: 256`、启动预热、强制 HTTP/2）；
- **流式**：SSE 缓冲来自 `sync.Pool`，手写 JSON 转义，每个增量立即 `Flush`，
  并设置 `X-Accel-Buffering: no`（否则 Nginx 会把整段流缓冲到结束）；
- **轮询转流式**：无条件节流（不会退化成忙轮询）、空轮询自适应退避、前缀差分还原 token 级增量；
  等待上游期间持续发送心跳，避免中间链路按空闲断开；
- **项目复用**：建项目比推理本身还慢，同一会话只建一次；无会话标识的请求轮转分桶；
- **账号粘性**：命中即续期；粘性账号仅因并发已满时短暂等待，而不是立刻换号；
- **指标**：`oaiprism_facade_first_delta_seconds` 直接衡量首字延迟。

## 用量计数

上游从不返回 usage（轮询响应的顶层与 payload 都没有这个字段），网关按本轮实际收发的内容自行计数：

- **分词**：官方 o200k_base 词表（与 tiktoken 校验的 sha256 一致，内嵌进二进制，运行时不联网）
  + 官方预切分正则 + 标准 BPE 合并，结果与 `tiktoken.encode_ordinary` 逐 token 一致。
  对拍样本：仓库全部源码与文档（41 万 token）、空白与换行的全部短组合、4500 条随机 Unicode，零差异；
- **输入**：真正发往上游的 input 条目（规整为 `[system, user]` 之后，即上游实际会读的内容），按 OpenAI 官方口径计入消息帧开销（每条 3 + 角色名，
  末尾回复引导 3）；图片按视觉计费规则（low 85；high/auto 缩放后按 512 切块，每块 170 + 85），
  data URI 解析真实宽高；
- **输出**：生成正文 + 推理文本，推理部分另记 `reasoning_tokens`（已含在输出内）；
- **去向**：同一组数字返回给客户端（Chat / Responses / Anthropic 三种 usage 结构），
  并写入请求流水，统计页按模型、按小时汇总；
- **防护**：BPE 原算法对单个超长片段是 O(n²)（2MB 连续字母会让计数永远算不完），
  长片段改用堆合并，O(n log n) 且合并顺序不变；Codex 每轮重发的历史块按内容缓存计数。

无法观测的部分不计：上游沙箱内部追加的系统提示与隐藏推理 token 不在收发内容里。
